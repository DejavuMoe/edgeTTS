# CI 检查消融实验与取舍

记录日期：2026-10-25（Asia/Taipei）。本报告研究 CI 检查的必要性；与
[业务机制消融实验](ablation.zh-CN.md) 是两组不同实验。

结论：保留 build、typecheck、lint、test、format:check。六个刻意选择的样本中，
每一项检查都有其他四项无法替代的检出能力。当前数据不支持删除任何一项门禁。
优先优化执行顺序、并行安排和构建缓存，不把“检查通过”误当成“没有风险”。

## 方法和数据范围

- 使用 [实验脚本](../../../scripts/ci-ablation.mjs)，每个样本在独立的临时副本中修改一个文件，
  不改正式源码或测试断言；即使某个检查失败，仍运行其余检查。
- 每轮包含前后两个干净基线和六个缺陷样本，每个副本运行五个命令，共 40 次命令执行。
  基线必须全部通过，六个样本必须全部被完整套件检出。
- 单项耗时取两个干净基线的均值；“移除一项”从实测检出矩阵中删除该检查的判定，
  并从串行命令总耗时中减去它的均值。这是判定消融，不是另外执行六条删减版工作流。
- 构建产物是后续检查的前提。移除 build 的判定不能直接删除全部构建执行；
  表中的耗时减少是上限，不能当作可直接获得的加速。
- 计时不包括副本复制、安装依赖、排队、网络审计、CodeQL、Docker、代理契约或发布。
  各进程计时使用未四舍五入的原始秒数计算，展示时才保留两位小数。
- 样本按检查类型刻意选取，包含格式和未使用变量等维护问题。检出率是这些样本上的比例，
  **不是线上缺陷检出率、安全覆盖率或所有检查同等重要的证明**。两个基线也不足以给出稳定的性能分位数。

仍需保留全量 pnpm audit 和每日依赖清单提交，详见 [安全 CI](../security-ci.md)。

## 保留与优化决策

1. **保留 build、typecheck、lint、test。** 各有独立职责。尤其不能因 build 已运行 TypeScript
   就删除 typecheck：测试代码的类型错误确实只被独立 typecheck 检出。
2. **保留 format:check，但它是低成本的一致性门禁。** 不是安全检测；适合在开发者提交前自动格式化，
   并在 CI 中靠前执行以尽早失败。上次远端仅约 4.22 秒，没有必要为省这点时间制造风格漂移。
3. **保留 CodeQL、依赖审计、Node/Bun 代理、Docker、Nginx、多架构与供应链检查。**
   六个质量样本没有测试这些检查的检出率，不能据此判为冗余。v1.0.1 修复中 Bun 1.4.2 的代理
   socket 清理问题就是必须在正式运行时验证的例子，Node 通过不能代替 Bun 通过。
4. **第一优化目标：调度。** lint 与格式检查不依赖构建，可以尽早执行；构建完成后再考虑
   将 typecheck 与 test 并行。必须等待全部进程并保留每个退出码，不能用后台命令掩盖失败。
   这可能减少墙钟等待，但共享 runner 的 CPU 竞争也可能抵消收益；当前没有测得该改动的加速值。
5. **第二优化目标：构建缓存。** v1.0.1 Docker 契约任务的镜像构建约 24 秒，发布阶段另有多架构构建。
   可复用受信任的 BuildKit 缓存，但仍应对最终待发布镜像及两个架构验收；不能拿源码测试替代产物验收。
6. **避免没有收益的拆 job。** 每个新 job 都要重新获取源码和工具链，测试与 typecheck 还依赖 workspace
   产物。先测同 job 内的安全并行，再决定是否拆 job。缓存命中和未命中都要测，不能只报告最好的一次。

本轮没有删除门禁，也没有声称尚未实施的并行或缓存方案已经提速。
原先五项质量检查的实验已经完成并复测；CodeQL 等项目提供的是实测成本与保留理由，
不是另一个伪造的“全 CI 缺陷检出率”。若未来要删除这些安全或部署门禁，应先为相应失效模式设计独立样本集。
