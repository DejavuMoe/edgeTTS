# CI 检查消融实验与取舍

记录日期：2026-10-25（Asia/Taipei）。本报告研究 CI 检查的必要性；与
[业务机制消融实验](ablation.zh-CN.md) 是两组不同实验。

结论：保留 build、typecheck、lint、test、format:check。六个刻意选择的样本中，
每一项检查都有其他四项无法替代的检出能力。当前数据不支持删除任何一项门禁。
优先优化执行顺序、并行安排和构建缓存，不把“检查通过”误当成“没有风险”。

前半部分保留首次质量消融及 PR #4 的历史证据；后续完成的 CodeQL、依赖、部署、
并行与缓存实验见文末“扩展消融与优化实测”。缓存是否采用由实测决定。

## 方法和数据范围

- 使用 [实验脚本](../../../scripts/ci-ablation.mjs)，每个样本在独立的临时副本中修改一个文件，
  不改正式源码或测试断言；即使某个检查失败，仍运行其余检查。
- 每轮包含前后两个干净基线和六个缺陷样本，每个副本运行五个命令，共 40 次命令执行。
  基线必须全部通过，六个样本必须全部被完整套件检出。
- 单项耗时取两个干净基线的均值；“移除一项”从实测检出矩阵中删除该检查的判定，
  并从串行命令总耗时中减去它的均值。这是判定消融，不是另外执行六条删减版工作流。
- 构建产物是后续检查的前提。移除 build 的判定不能直接删除全部构建执行；
  表中的耗时减少是上限，不能当作可直接获得的加速。
- 计时不包括副本复制、安装依赖、排队、网络审计、CodeQL、Docker、代理契约或发布。
  各进程计时使用未四舍五入的原始秒数计算，展示时才保留两位小数。
- 样本按检查类型刻意选取，包含格式和未使用变量等维护问题。检出率是这些样本上的比例，
  **不是线上缺陷检出率、安全覆盖率或所有检查同等重要的证明**。两个基线也不足以给出稳定的性能分位数。

## 保留与优化决策

1. **保留 build、typecheck、lint、test。** 各有独立职责。尤其不能因 build 已运行 TypeScript
   就删除 typecheck：测试代码的类型错误确实只被独立 typecheck 检出。
2. **保留 format:check，但它是低成本的一致性门禁。** 不是安全检测；适合在开发者提交前自动格式化，
   并在 CI 中靠前执行以尽早失败。上次远端仅约 4.22 秒，没有必要为省这点时间制造风格漂移。
3. **保留 CodeQL、依赖审计、Node/Bun 代理、Docker、Nginx、多架构与供应链检查。**
   六个质量样本没有测试这些检查的检出率，不能据此判为冗余。v1.0.1 修复中 Bun 1.4.2 的代理
   socket 清理问题就是必须在正式运行时验证的例子，Node 通过不能代替 Bun 通过。
4. **第一优化目标：调度。** lint 与格式检查不依赖构建，可以尽早执行；构建完成后再考虑
   将 typecheck 与 test 并行。必须等待全部进程并保留每个退出码，不能用后台命令掩盖失败。
   这可能减少墙钟等待，但共享 runner 的 CPU 竞争也可能抵消收益；当前没有测得该改动的加速值。
5. **第二优化目标：构建缓存。** v1.0.1 Docker 契约任务的镜像构建约 24 秒，发布阶段另有多架构构建。
   可复用受信任的 BuildKit 缓存，但仍应对最终待发布镜像及两个架构验收；不能拿源码测试替代产物验收。
6. **避免没有收益的拆 job。** 每个新 job 都要重新获取源码和工具链，测试与 typecheck 还依赖 workspace
   产物。先测同 job 内的安全并行，再决定是否拆 job。缓存命中和未命中都要测，不能只报告最好的一次。

本轮没有删除门禁，也没有声称尚未实施的并行或缓存方案已经提速。
原先五项质量检查的实验已经完成并复测；CodeQL 等项目提供的是实测成本与保留理由，
不是另一个伪造的“全 CI 缺陷检出率”。若未来要删除这些安全或部署门禁，应先为相应失效模式设计独立样本集。

### 实际故障检出与留一法

[扩展脚本](../../../scripts/ci-ablation-extended.mjs) 实际调用扫描器和部署测试，
不以手写 SARIF 代替 CodeQL，不以 mock 审计响应代替 pnpm audit。
每组都有前后干净对照；缺陷运行必须命中预期规则或错误信息，网络超时、缺少构建产物、
无效扫描结果和其他基础设施错误均不能计作检出。故障副本和镜像用后清理，不改正式测试断言。

12 个定向场景全部被检出，其中 10 个按现有门禁策略阻断，2 个中危 CodeQL 场景仅报告。
Node/Bun 两个场景是同一代理缺陷在两种运行时上的验收，不能当作两个独立的真实世界漏洞。

### 缓存对照与决定

两批共四轮使用不同 runner 和独立 GHA cache scope。每轮先执行正式 CI 原有的 `docker build`，
再用三个互不共享本地层缓存的 builder 测试冷缓存写入、远端缓存恢复和源码变化后的恢复。
计时包含 builder 初始化、缓存传输、镜像载入以及步骤间开销，不含随后单独执行的运行时验收。

| 场景                                    | a322197 第 1 轮 | a322197 第 2 轮 | 708f881 第 1 轮 | 708f881 第 2 轮 | 四轮均值 |
| --------------------------------------- | --------------: | --------------: | --------------: | --------------: | -------: |
| 原有 docker build，不接远端缓存         |         35.65 s |         25.84 s |         27.08 s |         30.71 s |  29.82 s |
| 首次构建并导出 GHA mode=max 缓存        |         63.26 s |         95.87 s |         55.81 s |         58.09 s |  68.26 s |
| 全新 builder 恢复相同源码的缓存         |          7.16 s |         10.07 s |          6.96 s |          7.52 s |   7.93 s |
| 修改源码后，全新 builder 恢复缓存并重建 |         28.85 s |         42.56 s |         25.72 s |         26.37 s |  30.88 s |

正确性验收全部通过：冷/热镜像 ID 相同；改动后的镜像 ID 不同且包含新增源码标记；
四种镜像都通过现有隔离运行时契约。日志明确记录远端 cache manifest 导入和 `CACHED` 层，
不是只在同一 builder 上重复构建所得的本地缓存假象。

**不把这套 mode=max 缓存加入单架构镜像验收任务。** 相同源码重跑平均快 73.4%，
但冷缓存平均慢 128.9%，源码变化的均值慢 3.5%，四轮收益方向也不一致。
第一批两轮的源码变化均值慢 16.2%；加入复测后差距缩小，但仍不能证明稳定收益。
四轮样本不足以证明长期加速，不能只拿 7.93 秒这一列作为采用依据。
现有多架构发布缓存保留；其平台构建、推送和缓存成本不同，本实验没有证明它应该删除。

### 拒绝四项全并行

最初尝试构建后同时运行 typecheck、lint、test、format。本地两个干净对照的均值从
32.16 秒降到 20.80 秒，六个缺陷也全部被拦住。但同一方案在远端第一个干净对照中，
`client-protocol.test.ts` 的背压排空测试触发原有 5000 ms 超时，实验因此失败。
[失败任务与日志](https://github.com/DejavuMoe/edgeTTS/actions/runs/40118913308/job/120945987922)
被保留；不能用重试通过或本地提速覆盖这个负面结果。

测试超时出现在四项并发期间，尚不足以证明 CPU 竞争是唯一原因。改为构建后仅并行三项静态检查，
等它们全部成功退出，再让测试套件独占这一阶段。测试断言、5000 ms 超时、provider 运行时代码均未修改。

### 采用静态检查并行

最终采用 `pnpm ci:parallel`：build → 并行 typecheck/lint/format → test。
这是候选提交 `708f881` 的真实命令执行对照，两个方案在同一 GitHub runner 上先后运行，
每个方案均有前后两个干净基线和六个缺陷样本，所有干净基线通过、六个缺陷均被检出。

| 调度                             | 远端前基线 | 远端后基线 |    均值 | 检出 |
| -------------------------------- | ---------: | ---------: | ------: | ---: |
| 五项串行                         |    62.87 s |    62.99 s | 62.93 s |  6/6 |
| 构建、静态检查并行、测试独占阶段 |    58.46 s |    57.41 s | 57.93 s |  6/6 |

实测减少 **5.00 秒 / 7.9%**。本地新方案两个基线为 25.50、25.65 秒，均通过；
本地与远端硬件不同，不混在同一个均值里。这里计时的是完整质量命令，未包含副本复制、依赖安装、
排队及其他 CI 任务，也没有声称整条发布流水线固定快 7.9%。样本没有随机交叉排序，
两个基线不足以作长期性能保证；但本轮没有依靠放宽测试或遗漏检查获得收益。

最终保留全部五项质量检查、两种 CodeQL、全依赖审计、Node/Bun 代理、Docker、Nginx、
多架构镜像与供应链门禁。Dependency Review 继续作为补充；本实验未证明 GitHub 原生支持
pnpm 12 的完整锁文件，也未注入 OS 漏洞、镜像签名伪造等超出本样本集的故障。

### CodeQL 告警 4

[告警 4](https://github.com/DejavuMoe/edgeTTS/security/code-scanning/4) 的根因是烟测直接记录上游 rejection，
可能把换行、凭据或合成文本带进日志。三个 smoke 入口及同类 benchmark 入口均改为固定失败消息，
保留非零退出行为，并直接执行这些入口的失败回调验证 Error 与字符串 rejection 不会泄漏内容。
没有新增忽略规则或降低 CodeQL 阻断阈值。

中危日志注入和无写权限 Actions 注入在实验中都被扫描器发现，却不会被现有高危/严重门禁阻断。
这是当前策略的明确边界：CI 通过不能代替对 code-scanning 告警的逐条处理。
