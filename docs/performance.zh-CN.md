# 长文本合成性能

2026-09-25 在 Debian WSL2 上对微软 Edge 在线服务实测，工作负载为同一段固定中英混合文本，按 300 码点切分为 8 段，约 196 秒 MP3 音频。项目架构见 [README](../README.zh-CN.md)。

## 方法与边界

基准脚本经真实的 `TtsService.synthesizeSegmented` 调用上游，各策略交替运行，以减少时段波动的影响，结果取中位数。记录每个音频块的到达时间，统计：

- **首字节**：请求开始到第一块音频到达。
- **段间空隙**：上一段最后一块到下一段第一块的间隔。
- **总耗时**：最后一块音频到达的时刻。不支持 MediaSource 的浏览器、下载完整文件的 API 客户端都要等到这一刻。
- **播放卡顿**：假设收到第一块即开始按实时速度播放，统计缓冲音频播完、需要等待新数据的总时长。

测量只覆盖一个地点和一条网络路径，每种策略 3 轮，结果受微软服务负载影响。数值用于比较策略，不代表其他环境下的绝对延迟。

## 结果

### 探索：三种候选策略

| 策略                         | 首字节 | 平均段间空隙 | 总耗时 | 上游连接 |
| ---------------------------- | ------ | ------------ | ------ | -------- |
| 每段新建连接（原实现）       | 2.15 s | 1.89 s       | 24.4 s | 8        |
| 同一连接依次合成各段         | 2.03 s | 0.37 s       | 9.4 s  | 1        |
| 每段新建连接，提前请求下一段 | 1.67 s | 1.17 s       | 18.5 s | 8        |

每段约 1.5–2 秒花在 TLS 与 WebSocket 握手上。微软服务在一轮合成结束后保持连接，同一连接可以继续合成下一段。预取只能掩盖部分握手时间，而且同时占用的上游连接数翻倍。

### 采用：会话复用连接

| 路径             | 首字节 | 平均段间空隙 | 总耗时 | 上游客户端 |
| ---------------- | ------ | ------------ | ------ | ---------- |
| 每段新建连接     | 1.90 s | 1.72 s       | 21.7 s | 8          |
| 会话（当前实现） | 2.35 s | 0.38 s       | 11.2 s | 1          |

总耗时下降约 48%，对微软的握手次数从每段一次降为每个请求一次。首字节时间两条路径结构相同：第一段都要建立一次连接，会话在连接已打开时的配置调用不经过网络。本轮 3 次测量中会话略高，但探索阶段复用策略又略低，差异在波动范围内。

三种策略的播放卡顿均为 0：每段约 24 秒音频只需约 2–3 秒即可到达，边下边播时缓冲足以覆盖段间空隙。连接复用的收益主要体现在总耗时，以及上游连接数上。

## 实现要点

- `TtsProvider.openSession` 是可选能力。不支持会话的提供方仍按段调用 `synthesize`，行为不变。
- 会话与并发许可同时释放，覆盖正常结束、出错、客户端中止和提前停止读取。
- 每段合成前重新确认连接：连接仍打开时不产生网络请求；服务端关闭空闲连接后，在 `EDGE_SETUP_TIMEOUT_MS` 内显式重连。不依赖 msedge-tts 在发送时的隐式重连，因为其重连失败不会被任何调用方处理。
- msedge-tts 在第二次调用 `setMetadata` 且未传选项时会抛出 `TypeError`，因此每次调用都传入空选项。

## 复现

```bash
pnpm install --frozen-lockfile
pnpm build
pnpm --filter @edgetts/tts-service bench 3
```

脚本会访问微软在线服务，每轮合成两次完整文本。探索阶段的三策略对比仅用于本次决策，脚本保留原实现与当前实现两条路径的对比。
